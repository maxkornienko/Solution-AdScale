# TO-BE: целевая архитектура AdScale

## 1. Архитектурный стиль

В первые 3 месяца AdScale переходит к модульному монолиту, а до конца года к микросервисам через Strangler Fig.

Почему не оставить монолит, почему не переписывать сразу на микросервисы и сравнение подходов описаны в [ADR-001](adr/ADR-001-evolution-strategy.md).

## 2. Целевая архитектура (через год)

Диаграмма: [C4_Container(TO-BE).puml](<diagrams/C4_Container(TO-BE).puml>)

### 2.1. Выделенные сервисы и обоснование границ

Модули гибридного монолита уже частично разделены по зонам ответственности: каждый станет отдельным сервисом со своей базой данных, где она нужна. Обращение к БД чужого сервиса напрямую – антипаттерн: только через сервис-владелец.

- **Bidding Service** – Ad Server и Auction Engine объединяются в один сервис ставок: принимает bid request, определяет пользователя, подбирает кандидатов, считает ставку и выбирает победителя. Так на пути bid request меньше сетевых вызовов: 3 вместо 5 при попадании в кеш, 4 вместо 7 при промахе. Своей БД нет: правила таргетинга берёт из Campaign, данные о пользователе – из bid request.
- **Campaign Service** – новый сервис хранения ставок и кампаний. Advertiser Dashboard пишет через Campaign Service. Bidding Service берёт данные из Redis, при промахе кеша вызывают Campaign Service, который читает свою реплику. Иначе массовые изменения кампаний в кабинете станут узким местом для ответов DSP-партнёрам.
- **Statistics Service + Analytics Service** – один деплой, разделённый на модули по CQRS. Statistics пишет показы и клики в PostgreSQL, Analytics читает ClickHouse. ClickHouse наполняется прямо из Kafka отдельной группой потребителей.


### 2.2. Взаимодействие между сервисами

- Внутренние вызовы между сервисами – gRPC.
- Внешние вызовы – HTTPS.
- Отклики пользователей (показы и клики) передаются в сервис статистики асинхронно через Kafka.


### 2.3. Инфраструктурные компоненты

- API Gateway (Envoy) – единая точка входа для всех внешних участников: DSP-партнёров, рекламодателей и пользователей.
  - маршрутизация и преобразование протокола: снаружи HTTPS, внутри все сервисы на gRPC;
  - аутентификация рекламодателей и внешних систем – для безопасности и надёжности;
  - rate limiting для пользователей: авторизация им не нужна, но нужна защита от DDoS-атак;
  - прослеживаемость состояния системы;
  - паттерны Retry и Circuit Breaker, стратегия повторов – экспоненциальный backoff с джиттером (jitter).
- Redis – кеш ставок и кампаний на пути bid request. Инвалидация по событию: при изменении ставок или кампаний Campaign Service удаляет запись из Redis, следующий запрос читает её из БД и снова кладёт в Redis.
- Redis – кеш HTML/JS-разметки баннеров для Delivery Service. Допущение: основная структура разметки не меняется, индивидуальна только её часть или вовсе ничего.
- Kafka – асинхронная передача откликов пользователей.
- Kubernetes – оркестрация: все сервисы работают в контейнерах.


### 2.4. Базы данных сервисов

| Сервис | БД | Назначение |
|---|---|---|
| Campaign | PostgreSQL + 2 реплики | Ставки, кампании и оплаченное количество показов по ставке. Advertiser Dashboard пишет через Campaign Service; Delivery уменьшает количество показов после каждого показа; при промахе кеша Campaign Service читает реплику для Bidding |
| Bidding | – | БД не предусмотрена |
| Delivery | PostgreSQL + реплика | Макеты, тексты – всё, что нужно для отображения рекламы и сборки разметки. Advertiser Dashboard пишет через Delivery Service, Delivery читает реплику |
| Statistics | PostgreSQL + асинхронная реплика | Показы и клики из Kafka |
| Analytics | ClickHouse | Аналитика по показам и кликам; данные поступают прямо из Kafka |
| Financial | PostgreSQL + синхронная реплика | Балансы и транзакции. Сумма списания определяется по данным Statistics; если баланса недостаточно – оплата через платёжный шлюз; затем транзакция и изменение баланса в БД |
