# Стратегия данных: Database per Service

У каждого сервиса своя база данных, где она нужна. Обращение к БД чужого сервиса напрямую запрещено: только через сервис-владелец.

## 1. База данных для каждого сервиса

| Сервис | Тип базы данных | Обоснование |
|---|---|---|
| Сервис ставок (Bidding) | своей БД нет; Redis – кеш ставок и кампаний | Сервис stateless: ставки, кампании и правила таргетинга читает из Redis, при промахе кеша – через Campaign Service |
| Сервис кампаний (Campaign) | PostgreSQL: основная + 2 реплики | Ставки, кампании и оплаченное количество показов. Пишет Advertiser Dashboard через Campaign Service; при промахе кеша Campaign Service читает реплики для Bidding |
| Сервис статистики (Statistics) | PostgreSQL: основная + асинхронная реплика | Профиль OLTP: тысячи коротких записей показов и кликов в секунду. PostgreSQL заточен под такую нагрузку. Надёжный учёт событий без дублей: ClickHouse отсекает дубли с задержкой, а по событиям списываются деньги |
| Сервис аналитики (Analytics) | ClickHouse | Профиль OLAP: тяжёлые запросы по большим объёмам, например суммы показов по кампаниям за период. PostgreSQL на таких объёмах медленный, ClickHouse заточен под аналитику |
| Сервис финансов (Financial) | PostgreSQL: основная + синхронная реплика | Балансы и транзакции. Сумма списания определяется по данным Statistics пакетом раз в несколько минут: там события без дублей; если баланса недостаточно – оплата через платёжный шлюз |
| Delivery | PostgreSQL: основная + реплика; Redis – кеш разметки | Макеты, тексты, всё для сборки разметки. Пишет Advertiser Dashboard через Delivery Service, Delivery читает реплику |

## 2. Отказоустойчивость данных

### 2.1. RPO и RTO для каждого сервиса

| Сервис | RPO | RTO | Почему так |
|---|---|---|---|
| Campaign | 5 минут | минуты | На пути ставки: без Campaign партнёр получает только no-bid. Потеря данных терпима |
| Delivery | 5 минут | минуты | На пути ставки: без разметки ответа партнёру нет. Потеря данных терпима |
| Statistics | 0 | минуты | По событиям списываются деньги. Потерянное можно дочитать из Kafka, события хранятся 7 дней |
| Analytics (ClickHouse) | 0 | часы | Важно, но данные можно перечитать из Kafka в течение 7 дней |
| Financial | 0 | 1 час | Балансы и транзакции терять нельзя, но списание пакетное – час простоя не критичен |

### 2.2. Стратегия резервного копирования

Реплика не заменяет бэкап: ошибочное удаление или изменение данных реплика повторит за миллисекунды. Поэтому для PostgreSQL используется схема GFS с непрерывной архивацией WAL – это позволяет восстановиться на любой момент времени (point-in-time recovery). Бэкапы хранятся отдельно от БД.

| Бэкап | Частота | Срок хранения |
|---|---|---|
| Полный + непрерывный WAL | ежедневно | 30 дней |
| Еженедельный | раз в неделю | 12 недель |
| Ежемесячный | раз в месяц | 12 месяцев; для Financial – 5 лет (402-ФЗ о бухгалтерском учёте) |

| Хранилище | Бэкап |
|---|---|
| PostgreSQL: Campaign, Delivery, Statistics, Financial | по схеме выше |
| ClickHouse (Analytics) | отдельно не бэкапится: данные перестраиваются из Statistics DB, где хранятся все события |
| Redis | не бэкапится: после перезапуска кеш прогревается джобой |
| Kafka | не бэкапится: буфер событий на 7 дней |

### 2.3. Соответствие принципам 12-факторных приложений

Подход – контейнеризация и оркестрация: все сервисы работают в контейнерах под управлением Kubernetes.

| Принцип | Как выполняется в AdScale |
|---|---|
| Кодовая база | У каждого сервиса одна кодовая база; из неё собирается один образ контейнера для всех сред |
| Зависимости | Зависимости упакованы в образ контейнера и явно объявлены |
| Конфигурация | Конфигурация не зашивается в образ: передаётся через оркестратор (ConfigMap и Secret в Kubernetes) |
| Сторонние службы | PostgreSQL, ClickHouse, Redis и Kafka – отдельные ресурсы, сервисы подключаются к ним по сети |
| Сборка и запуск | Образ собирается в CI, выпуск – образ плюс конфигурация, запуск и обновление – через Kubernetes. Ручной деплой уходит |
| Процессы | Bidding Service stateless: состояния не хранит, данные берёт из Redis и Campaign Service |
| Привязка портов | Каждый сервис слушает свой gRPC-порт в контейнере; снаружи доступен только API Gateway (Envoy) |
| Параллелизм | Горизонтальное масштабирование: Kubernetes добавляет экземпляры stateless-сервисов, например Bidding, по нагрузке |
| Расположение данных | Данные хранятся только во внешних хранилищах, у каждого сервиса своя БД; контейнеры данных не хранят |
| Ведение логов | Сервисы пишут логи в stdout как поток событий, оркестратор собирает их централизованно; метрики и трассировку запросов даёт Envoy |
| Администрирование | Прогрев кеша – разовая задача: отдельная джоба (Job в Kubernetes) запускается перед тем, как пустить трафик на новый Redis |
| Среды разработки, тестирования и эксплуатации | Во всех средах одни и те же образы контейнеров; различается только конфигурация |
