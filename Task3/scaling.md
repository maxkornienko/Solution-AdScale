# Масштабирование баз данных

## 1. Репликация Master-Slave

| Сервис | Схема | Кто пишет | Кто читает реплику |
|---|---|---|---|
| Campaign | основная + 2 реплики | Advertiser Dashboard через Campaign Service | Campaign Service при промахе кеша Bidding |
| Delivery | основная + реплика | Advertiser Dashboard через Delivery Service | Delivery Service при сборке разметки |
| Statistics | основная + асинхронная реплика | Statistics (показы и клики из Kafka) | никто: реплика для переключения при аварии (RTO – минуты) |
| Financial | основная + синхронная реплика | Financial Service | никто: реплика для RPO = 0 и переключения при аварии |

## 2. Шардирование: какие данные и по какому ключу

Шардируются показы в Statistics DB: они растут быстрее всего и без остановки, показов в 100–1000 раз больше, чем кликов.

Способ – хешированное шардирование по id события: номер шарда = хеш(`event_id`) mod число шардов.

Почему этот ключ:
- главный запрос к Statistics DB – проверка дубля «есть ли событие с таким id?», и он всегда попадает в один шард;
- запись распределяется по шардам равномерно, крупная кампания не перегружает отдельный шард;
- подсчёт показов по кампании для Financial идёт пакетом раз в несколько минут, поэтому обойти для него все шарды допустимо; аналитические запросы по кампаниям и периодам идут в ClickHouse;
- тот же ключ используется для партиционирования в Kafka.

## 3. Read replicas для сервиса аналитики

Не нужны: аналитика вынесена в отдельное хранилище под OLAP-нагрузку – ClickHouse. Тяжёлые аналитические запросы не касаются PostgreSQL, куда Statistics пишет события.

## 4. Где применимо CQRS

Statistics + Analytics – один деплой, разделённый на модули по CQRS. Модель записи: модуль Statistics пишет показы и клики в PostgreSQL. Модель чтения: модуль Analytics строит отчёты по ClickHouse. Обе модели наполняются из одного топика Kafka разными группами потребителей.
