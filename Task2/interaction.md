# Схема взаимодействия и выбор протоколов

## 1. Внутреннее взаимодействие

Внутренние вызовы между сервисами, включая Bidding → Campaign, идут по gRPC, а не по REST.

Почему gRPC:
- одно соединение HTTP/2, много параллельных запросов – не тратим время на открытие соединений при 18 000 запросов в секунду;
- сообщения в двоичном формате Protobuf меньше, сериализация быстрее, чем у JSON.

Цена: двоичные сообщения не прочитать глазами – логи и отладку читать сложнее.

## 2. Внешнее взаимодействие с DSP

С DSP-партнёрами AdScale общается по HTTPS в формате OpenRTB: это отраслевой стандарт, он уже задан, и партнёры работают по нему. API Gateway принимает запросы по HTTPS и передаёт их внутрь по gRPC.

## 3. Потоковая обработка событий

Показы и клики передаются в Statistics асинхронно через Kafka.

Kafka буферизует показы и клики: Delivery публикует событие и не ждёт записи, а Statistics забирает события и пишет их в своём темпе. Так выполняется драйвер «Запись событий не замедляет чтение ставок и кампаний».

Кроме того, Kafka хранит события: если показ или клик не записался в Statistics, событие можно перечитать из топика. Это надёжнее для фиксации показов и кликов. Повторно прочитанное событие не посчитается дважды: у каждого показа и клика свой идентификатор (см. идемпотентность в [bidding-service.md](bidding-service.md), раздел 5.3).

## 4. Нужен ли API Gateway и какой

Нужен: единая точка входа для всех внешних участников. Выбран Envoy, обоснование и дизайн – в [api-gateway.md](api-gateway.md).
