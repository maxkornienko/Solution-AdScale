# Спецификация сервиса ставок (Bidding Service)

Диаграмма компонентов: [component-bidding-service.puml](diagrams/component-bidding-service.puml)

## 1. Границы сервиса

Bidding Service объединяет бывшие Ad Server и Auction Engine: принимает bid request, определяет пользователя, подбирает кандидатов, считает ставку и выбирает победителя. Своей БД нет (stateless).

Вне границ сервиса:
- Campaign Service – хранит кампании, ставки-настройки рекламодателей и оплаченное количество показов;
- Delivery Service – формирует HTML/JS-разметку баннера;
- API Gateway – принимает запросы DSP-партнёров и передаёт их в Bidding Service.

Почему объединены: на пути bid request меньше сетевых вызовов – 3 вместо 5 при попадании в кеш, 4 вместо 7 при промахе.

## 2. API

Сервис предоставляет одну операцию: принимает bid request и отдаёт bid response. Вызывает её API Gateway по gRPC. Остальные данные сервис запрашивает сам (см. раздел 3).

Если ставить не будем (нет подходящих кампаний, закончились оплаченные показы), сервис возвращает признак no-bid, а API Gateway отвечает партнёру HTTP 204 No Content в пределах `tmax`.

## 3. Зависимости

Все зависимости синхронные.

| Зависимость | Что берём | Если недоступна |
|---|---|---|
| Redis | ставки, кампании, правила таргетинга | обращаемся к Campaign Service через Circuit Breaker |
| Campaign Service | то же при промахе кеша | no-bid |
| Delivery Service | HTML/JS-разметка победителя | no-bid |

## 4. Модель данных

Bidding Service своей БД не имеет. Он работает с такими сущностями:

| Сущность | Поля | Откуда |
|---|---|---|
| Bid request | по стандарту OpenRTB: id запроса, показ (формат, размер, минимальная цена), сайт или приложение, устройство, пользователь, `tmax` | от DSP-партнёра через API Gateway |
| Кампания | id, статус (активна / на паузе / оплаченные показы исчерпаны), ставка, таргетинговые данные для принятия решения, id креативов | Redis, при промахе – Campaign Service |
| Победитель | id победившей кампании, id креатива | передаётся в Delivery Service |
| Разметка баннера | HTML/JS-разметка | от Delivery Service |
| Bid response | по стандарту OpenRTB: id запроса, цена, разметка (`adm`), id кампании, id креатива; при no-bid – HTTP 204 | в DSP-партнёр через API Gateway |

## 5. Паттерны надёжности

### 5.1. Circuit Breaker для вызовов зависимых сервисов

Circuit Breaker стоит на вызовах Bidding Service → Campaign Service. Он не даёт падению Redis перегрузить Campaign Service и реплики Campaign DB: без него все 18 000 запросов в секунду разом ушли бы в две реплики.

Пока цепь разомкнута, Bidding Service отвечает no-bid (HTTP 204): лучше ответить, чем молчать. Восстановление через состояние half-open: в Campaign Service пропускается понемногу пробных запросов, и только если они успешны, цепь замыкается.

### 5.2. Повторные попытки с экспоненциальной задержкой

Повторы с экспоненциальным backoff и джиттером ставим на API Gateway:
- для показов и кликов пользователей – чтобы не потерять важный для бизнеса показ или клик, за который платят;
- для запросов рекламодателей.

На пути bid request повторов нет: при долгом тайм-ауте или большом числе повторов время выйдет, и ответ партнёру потеряет смысл. Вместо повтора – no-bid.

### 5.3. Идемпотентность финансовых операций

Повторы показов и кликов на API Gateway без идемпотентности приведут к списанию денег за каждый повтор. Поэтому запросы, за которые списываются деньги, делаются идемпотентными.

У каждого такого запроса есть уникальный идентификатор. При получении сервис записывает его в БД; если запрос с таким идентификатором уже обработан, повтор не обрабатывается и деньги повторно не списываются.

Идентификатор генерирует API Gateway и передаёт дальше в заголовке. При повторе шлюз не создаёт новый идентификатор, а отправляет тот же.

### 5.4. Резервные стратегии (кэшированные или дефолтные ставки)

Основная резервная стратегия – no-bid (HTTP 204): данные в памяти могут быть не обновлены, а ставка по устаревшим данным рискует потратить деньги рекламодателя сверх бюджета.

Кэшированные данные (снимок настроек кампаний с ограничением по возрасту) допустимы только по согласованию с бизнесом: это возможный небольшой перерасход бюджета в обмен на меньшее число упущенных показов.

Дефолтную ставку не используем: сервис не знает, какой кампании она подходит и есть ли у неё деньги.
